Chapter 10

Pick & Place Capstone

This is the chapter where everything comes together. You will write a complete program that makes the Panda arm pick up an object from one location and place it somewhere else — handling every step from opening the gripper to returning home. Nothing here is conceptually new; it combines the tools from Chapters 4–9 into one working application. Think of it as the final project for the tutorial. If something feels unfamiliar, the chapter references will point you back to exactly where it was introduced.

Key Terms — Chapter 10

Finite state machine (FSM)
A control structure that models a complex task as a set of discrete states (e.g., APPROACH, GRASP, LIFT, TRANSPORT) with transitions triggered by conditions; makes multi-step tasks easy to debug and restart.
State
One step in the FSM; each state does exactly one thing and then checks whether to continue or report an error.
Transition
The switch from one FSM state to another, triggered by a condition such as "gripper is closed AND object is detected."
Pre-grasp pose
A pose above the object, reached before the Cartesian descent; ensures the arm approaches from above and does not knock the object sideways.
Cartesian descent
A straight downward movement in Cartesian space (constant x and y, decreasing z) from the pre-grasp pose to the grasp pose, computed by compute_cartesian_path.
Cartesian straight-line path
A path in which the end-effector moves in a straight line in Cartesian space; critical for vertical pick-and-place descents to avoid dragging the object sideways.
Grasp action
The franka_gripper action that closes the fingers to a target width with a target force and confirms whether an object was gripped.
Path fraction
The proportion of the requested Cartesian waypoints that could be reached collision-free; a fraction below the threshold (e.g., 0.95) causes the move to be aborted.
Retract pose
A pose above the place location, reached after releasing the object; lifts the gripper clear before the final return-to-home move.
Node graph
A diagram showing all the ROS 2 nodes active during the task and the topics/services/actions connecting them.

10.1 Task Overview

The task: the Panda starts in its home configuration. A cylindrical object sits on a table at a known position. The robot must:

  1. Open the gripper.
  2. Move the EEF to a pre-grasp pose (10 cm above the object).
  3. Descend straight down to the grasp pose.
  4. Close the gripper.
  5. Lift the object 15 cm.
  6. Transport it to the goal location (Cartesian straight-line).
  7. Lower it to the place pose.
  8. Open the gripper to release.
  9. Retract upward and return to home.

Each of those steps draws on a specific skill from an earlier chapter: steps 3, 5, 6, and 7 use the compute_cartesian_path technique from Chapter 5; steps 4 and 8 use the gripper action interface first seen in Chapter 8's deep dive; and step 2 relies on the joint-space planner from Chapter 4 to reach the pre-grasp pose without constraining the path.

This is a nine-step deterministic sequence. We encode it as a finite state machine (FSM) so that each step is atomic and failures can be caught and handled state-by-state. The FSM pattern also makes debugging straightforward: when the arm stops unexpectedly, the logger tells you exactly which state failed and why.

10.2 Finite State Machine Design

Why use a finite state machine instead of a flat sequence of function calls? Because real hardware fails in unexpected ways. A flat sequence crashes the whole program the moment a gripper action times out; an FSM gracefully transitions to ERROR, logs the failing state, and stops all motion safely — exactly the behaviour you practised in Chapter 9's emergency-stop discussion. Each state in the FSM does exactly one job, which also makes testing easier: you can jump the arm to the GRASP state in isolation and confirm the gripper closes correctly without re-running the entire approach sequence.

Each state is a Python method that returns True (success, advance to next state) or False (failure, enter ERROR state). The main loop iterates the state list until DONE or ERROR is reached. This is the same principle behind the ROS 2 action feedback loop described in Chapter 4 — a long-running task broken into stages with a clear success/failure result at each stage. The key difference here is that you are the one designing the stages.

10.4 EEF Trajectory

The FSM states from §10.2 each move the end-effector somewhere. Figure 10.3 shows exactly where — a side-view map of the complete end-effector path. Designing this trajectory carefully is one of the most important decisions in pick-and-place: the wrong path sequence will knock the object sideways or collide with the table on the way down. Recall from Chapter 5 that the end-effector's Cartesian pose has six degrees of freedom — position and orientation — and that every waypoint in the path must specify both.

The critical design choice: all vertical and horizontal segments are Cartesian straight-lines (computed with compute_cartesian_path from Chapter 5). This ensures the object moves in a predictable path — important when working near other objects on a cluttered table. Why does this matter? Recall from Chapter 5 that an OMPL-planned path moves through joint space and the end-effector traces a curved arc in Cartesian space. If you are holding a fragile object, a surprise arc could swing it into something. Cartesian straight-line paths remove that uncertainty entirely. The initial HOME→PRE-GRASP move and the final RETRACT→HOME move are left to the OMPL planner because no object is held and path shape does not matter — any collision-free path is acceptable.

10.5 Full Implementation

Before running this code, make sure the simulation stack is running (see §3.5). In simulation: start with launch_sim.sh. On real hardware: follow the four-terminal sequence from §9.4. Then run pick_and_place.py in a separate terminal with your workspace sourced.

The code below is the complete pick-and-place node. Read it in sections: the task parameters at the top are the only numbers you need to change for a different object or table layout; the helper methods (_plan_to_pose, _cartesian_move, and the gripper wrappers) are reusable in any future project; and the FSM runner at the bottom maps directly to the state diagram in Figure 10.1. The MoveItPy interface used here was explained in detail in Chapter 8 — if a method call looks unfamiliar, that is where to look it up. 

#!/usr/bin/env python3
"""
pick_and_place.py — complete FSM-based pick-and-place capstone.

Assumes:
  - franka_ros2 and MoveIt 2 are running (sim or real hardware)
  - Franka Hand gripper controller is active
  - Object is at PICK_POSE; goal is PLACE_POSE
"""
import enum
import time
import rclpy
from rclpy.node import Node
from rclpy.action import ActionClient
from geometry_msgs.msg import PoseStamped
import moveit_py
from moveit.planning import MoveItPy, PlanRequestParameters
from franka_msgs.action import Grasp, Move as GripperMove


# ── Task parameters ──────────────────────────────────────────────────────────
PICK_X, PICK_Y, PICK_Z    = 0.40,  0.00, 0.12   # object centre (m)
PLACE_X, PLACE_Y, PLACE_Z = 0.40,  0.30, 0.12   # goal centre (m)

APPROACH_HEIGHT = 0.10   # m above pick/place pose for pre-grasp / retract
LIFT_HEIGHT     = 0.15   # m to lift after grasping

GRIPPER_WIDTH_OPEN  = 0.08   # m
GRIPPER_WIDTH_CLOSE = 0.03   # m — adjust to object diameter
GRIPPER_FORCE       = 40.0   # N

VEL_SCALE  = 0.25
ACC_SCALE  = 0.10
CART_STEP  = 0.005   # m — interpolation step for Cartesian paths
MIN_FRAC   = 0.95    # minimum fraction for compute_cartesian_path


class State(enum.Enum):
    INIT        = 0
    PRE_GRASP   = 1
    DESCEND     = 2
    GRASP       = 3
    LIFT        = 4
    TRANSPORT   = 5
    PLACE       = 6
    RELEASE     = 7
    RETRACT     = 8
    DONE        = 9
    ERROR       = 10


# ── Helper: build a PoseStamped ───────────────────────────────────────────────
def _pose(x: float, y: float, z: float,
          qx: float = 1.0, qy: float = 0.0,
          qz: float = 0.0, qw: float = 0.0) -> PoseStamped:
    p = PoseStamped()
    p.header.frame_id     = 'panda_link0'
    p.pose.position.x     = x
    p.pose.position.y     = y
    p.pose.position.z     = z
    p.pose.orientation.x  = qx
    p.pose.orientation.y  = qy
    p.pose.orientation.z  = qz
    p.pose.orientation.w  = qw
    return p


# ── Main node ─────────────────────────────────────────────────────────────────
class PickAndPlaceNode(Node):
    def __init__(self):
        super().__init__('pick_and_place')

        self.moveit: MoveItPy = moveit_py.MoveItPy(
            node_name='pick_and_place')
        self.arm  = self.moveit.get_planning_component('panda_arm')
        self.hand = self.moveit.get_planning_component('panda_hand')

        self._grasp_client = ActionClient(
            self, Grasp, '/franka_gripper/grasp')
        self._move_client  = ActionClient(
            self, GripperMove, '/franka_gripper/move')

        self.get_logger().info('Pick-and-place node ready.')

    # ── Gripper helpers ───────────────────────────────────────────────────────
    def _gripper_move(self, width: float, speed: float = 0.05) -> bool:
        goal        = GripperMove.Goal()
        goal.width  = width
        goal.speed  = speed
        self._move_client.wait_for_server(timeout_sec=5.0)
        future = self._move_client.send_goal_async(goal)
        rclpy.spin_until_future_complete(self, future, timeout_sec=10.0)
        result_future = future.result().get_result_async()
        rclpy.spin_until_future_complete(self, result_future, timeout_sec=10.0)
        return result_future.result().result.success

    def _gripper_grasp(self, width: float, force: float) -> bool:
        goal           = Grasp.Goal()
        goal.width     = width
        goal.speed     = 0.05
        goal.force     = force
        goal.epsilon.inner = 0.005
        goal.epsilon.outer = 0.005
        self._grasp_client.wait_for_server(timeout_sec=5.0)
        future = self._grasp_client.send_goal_async(goal)
        rclpy.spin_until_future_complete(self, future, timeout_sec=15.0)
        result_future = future.result().get_result_async()
        rclpy.spin_until_future_complete(self, result_future, timeout_sec=15.0)
        return result_future.result().result.success

    # ── Arm helpers ───────────────────────────────────────────────────────────
    def _plan_to_pose(self, target: PoseStamped) -> bool:
        self.arm.set_start_state_to_current_state()
        self.arm.set_goal_state(
            pose_stamped_msg=target, pose_link='panda_hand')
        params = PlanRequestParameters(self.moveit, 'panda_arm')
        params.max_velocity_scaling_factor     = VEL_SCALE
        params.max_acceleration_scaling_factor = ACC_SCALE
        plan = self.arm.plan(single_plan_parameters=params)
        if not plan:
            return False
        return bool(self.moveit.execute(plan.trajectory, controllers=[]))

    def _cartesian_move(self, waypoints: list) -> bool:
        self.arm.set_start_state_to_current_state()
        plan, fraction = self.arm.compute_cartesian_path(
            waypoints=waypoints,
            max_step=CART_STEP,
            jump_threshold=0.0,
        )
        if fraction < MIN_FRAC:
            self.get_logger().warn(
                f'Cartesian path fraction {fraction:.2f} < {MIN_FRAC}')
            return False
        return bool(self.moveit.execute(plan.trajectory, controllers=[]))

    # ── FSM state handlers ────────────────────────────────────────────────────
    def state_init(self) -> bool:
        self.get_logger().info('State: INIT — opening gripper.')
        return self._gripper_move(width=GRIPPER_WIDTH_OPEN)

    def state_pre_grasp(self) -> bool:
        self.get_logger().info('State: PRE-GRASP — moving above object.')
        target = _pose(PICK_X, PICK_Y, PICK_Z + APPROACH_HEIGHT)
        return self._plan_to_pose(target)

    def state_descend(self) -> bool:
        self.get_logger().info('State: DESCEND — Cartesian straight down.')
        return self._cartesian_move([_pose(PICK_X, PICK_Y, PICK_Z)])

    def state_grasp(self) -> bool:
        self.get_logger().info('State: GRASP — closing gripper.')
        return self._gripper_grasp(GRIPPER_WIDTH_CLOSE, GRIPPER_FORCE)

    def state_lift(self) -> bool:
        self.get_logger().info('State: LIFT — Cartesian straight up.')
        return self._cartesian_move(
            [_pose(PICK_X, PICK_Y, PICK_Z + LIFT_HEIGHT)])

    def state_transport(self) -> bool:
        self.get_logger().info('State: TRANSPORT — Cartesian straight to goal.')
        return self._cartesian_move(
            [_pose(PLACE_X, PLACE_Y, PLACE_Z + LIFT_HEIGHT)])

    def state_place(self) -> bool:
        self.get_logger().info('State: PLACE — lowering object.')
        return self._cartesian_move([_pose(PLACE_X, PLACE_Y, PLACE_Z)])

    def state_release(self) -> bool:
        self.get_logger().info('State: RELEASE — opening gripper.')
        return self._gripper_move(width=GRIPPER_WIDTH_OPEN)

    def state_retract(self) -> bool:
        self.get_logger().info('State: RETRACT — returning to home.')
        return self._cartesian_move(
            [_pose(PLACE_X, PLACE_Y, PLACE_Z + APPROACH_HEIGHT)])

    # ── FSM runner ────────────────────────────────────────────────────────────
    def run(self) -> None:
        handlers = [
            (State.INIT,      self.state_init),
            (State.PRE_GRASP, self.state_pre_grasp),
            (State.DESCEND,   self.state_descend),
            (State.GRASP,     self.state_grasp),
            (State.LIFT,      self.state_lift),
            (State.TRANSPORT, self.state_transport),
            (State.PLACE,     self.state_place),
            (State.RELEASE,   self.state_release),
            (State.RETRACT,   self.state_retract),
        ]

        current = State.INIT
        for state, handler in handlers:
            current = state
            self.get_logger().info(f'--- Entering state: {state.name} ---')
            success = handler()
            if not success:
                self.get_logger().error(
                    f'State {state.name} failed. Entering ERROR.')
                current = State.ERROR
                break
            time.sleep(0.2)   # brief pause between states

        if current != State.ERROR:
            current = State.DONE
            self.get_logger().info('=== Pick-and-place DONE ===')
        else:
            self.get_logger().error('=== Pick-and-place FAILED ===')


def main():
    rclpy.init()
    node = PickAndPlaceNode()
    rclpy.spin_once(node, timeout_sec=2.0)   # allow discovery
    node.run()
    node.destroy_node()
    rclpy.shutdown()


if __name__ == '__main__':
    main()
Before running on real hardware: complete the Chapter 9 safety checklist, set VEL_SCALE = 0.05 for the first run, and keep your hand on the E-stop. Increase speed only after confirming the full sequence in simulation. Remember from Chapter 9 that the real arm has calibration and network-latency differences that can shift the actual grasp pose by a few millimetres — add a small tolerance to epsilon.inner and epsilon.outer so the grasp action does not reject a successful grip just because the finger position is slightly off.
Chapter 10 Summary
  • Pick-and-place is the "hello world" of robot arm programming — and completing it requires every skill built in Chapters 2–9: kinematics (Ch 2), simulation (Ch 3), joint-space and Cartesian planning (Ch 4–5), velocity-aware motion (Ch 6), safe contact (Ch 7), obstacle-aware planning (Ch 8), and hardware transition (Ch 9). Nothing in this chapter is new machinery; the chapter is about integration. That is the point.
  • A finite state machine (FSM) is the right way to structure any multi-step robot task. Each state (APPROACH → DESCEND → GRASP → LIFT → TRANSPORT → PLACE → RETREAT) does exactly one thing; transitions are triggered by success or failure, not by time. This makes the sequence readable, pausable, and safe — you can see exactly which state failed and why.
  • The key physical rule: always approach from above (pre-grasp pose) before descending straight down to the grasp. Commanding the gripper directly to the grasp pose in joint space causes the gripper to arc sideways, knocking the object off position before the fingers close. Cartesian descent solves this.
  • For hardware deployment, follow Chapter 9's protocol without shortcuts: 10% speed first, verify each FSM state transition manually, keep your hand on the E-stop. The full sequence should run reliably in simulation at 100% speed before any hardware run begins.

10.6 Bonus Project: Visualizing Pick & Place in Isaac Sim

Everything you built in §10.5 runs inside Gazebo — a fast, lightweight physics simulator. You set up Gazebo in Chapter 3, and it has been the testing environment for every chapter since. Gazebo is ideal for testing control code because it integrates directly with ros2_control and runs on any laptop. But it has a visible limitation: the 3D rendering looks like a game engine from 2005.

NVIDIA Isaac Sim is a different kind of simulator. Instead of cartoon-style graphics, it uses path-tracing (the same technique used in movie visual effects) to produce photorealistic images with real lighting, shadows, reflections, and material finishes. In the image below, it is often impossible to tell an Isaac Sim render from a real photograph.

Why does photorealistic rendering matter for robotics? If you want to train a neural network to recognize whether the gripper has grabbed a cube, you need thousands of example images. Filming a real robot picking up objects is slow and expensive. Isaac Sim generates those images automatically and, because the rendering looks nearly identical to real camera footage, a model trained on synthetic images actually works on real hardware. This technique is called sim-to-real transfer.

10.6.1 What You Need

  • GPU: NVIDIA RTX 20xx or newer (ray-tracing hardware is required for photorealistic mode)
  • Isaac Sim 4.x: Free download from NVIDIA — search "Isaac Sim" on developer.nvidia.com and install via the Omniverse Launcher
  • Python 3.10: Isaac Sim ships its own Python environment; you run scripts inside it
  • Disk space: ~30 GB for Isaac Sim + assets
No GPU? Isaac Sim can run in CPU-only mode with basic rendering — it is slower and less photorealistic, but the Python API is identical. You can still follow all the code examples below.

10.6.2 Step 1 — Load the Panda Robot

Isaac Sim includes a built-in Franka Panda asset. The code below creates a simulation world, loads the robot, adds a red cube, and starts the physics engine. Run it in Isaac Sim's built-in Script Editor (menu: Window → Script Editor).

Before reading the code, here are the new terms you will see:

  • prim_path — a file-system-like path that identifies every object in the Isaac Sim scene (e.g., /World/Panda). Think of it like a folder path on your computer.
  • World — the Isaac Sim equivalent of a Gazebo world: it holds all objects and runs the physics simulation step by step.
  • DynamicCuboid — a physics-enabled cube that responds to gravity and collisions (as opposed to a static prop).
scene_setup.py — run in Isaac Sim Script Editor 

# Step 1: Create the simulation app (opens the Isaac Sim window)
from omni.isaac.kit import SimulationApp
simulation_app = SimulationApp({"headless": False})  # headless=True for no GUI

import numpy as np
from omni.isaac.core import World
from omni.isaac.franka import Franka
from omni.isaac.core.objects import DynamicCuboid

# ── Create the world ─────────────────────────────────────
world = World(stage_units_in_meters=1.0)   # 1 unit = 1 metre

# ── Add the Franka Panda robot ────────────────────────────
# Isaac Sim knows the Panda URDF; just give it a scene path
robot = world.scene.add(
    Franka(prim_path="/World/Panda", name="panda")
)

# ── Add a red cube to pick up ─────────────────────────────
# Position: 0.5 m in front of the robot, 2.5 cm above the floor
cube = world.scene.add(
    DynamicCuboid(
        prim_path="/World/RedCube",
        name="red_cube",
        position=np.array([0.5, 0.0, 0.025]),   # x, y, z in metres
        scale=np.array([0.05, 0.05, 0.05]),      # 5 cm × 5 cm × 5 cm
        color=np.array([1.0, 0.0, 0.0]),         # R, G, B (red)
    )
)

# ── Reset the scene to apply all settings ─────────────────
world.reset()
print("Scene ready. Robot and cube loaded.")

# ── Run 50 physics steps so the scene settles ────────────
for _ in range(50):
    world.step(render=True)

After running this, you should see the Panda arm in its home configuration with a red cube sitting on the floor in front of it, exactly as in the Gazebo version.

10.6.3 Step 2 — Replay the Pick Trajectory

Isaac Sim lets you set joint angles directly with robot.set_joint_positions(). The function below smoothly interpolates the arm from its current configuration to a target joint configuration — the same waypoints used in §10.5. Notice that Isaac Sim bypasses ROS 2 entirely and drives joints directly; this is why it is better suited for training data generation than for testing real control code, where you want to exercise the full ROS 2 communication stack.

What are these joint angle numbers? Each number is the angle of one joint in radians. The Panda has 7 joints, so each configuration is a list of 7 numbers. For reference: 0.785 rad ≈ 45°, 1.571 rad ≈ 90°, 2.356 rad ≈ 135°. The home pose [0, −0.785, 0, −2.356, 0, 1.571, 0.785] is the standard Panda ready position — arm slightly bent, pointing upward.
replay_trajectory.py — run after scene_setup.py 

# Joint configurations matching the §10.5 pick-and-place poses
HOME_JOINTS      = [0.0, -0.785, 0.0, -2.356, 0.0,  1.571, 0.785]
PRE_GRASP_JOINTS = [0.0,  0.200, 0.0, -2.000, 0.0,  2.200, 0.785]
GRASP_JOINTS     = [0.0,  0.350, 0.0, -1.850, 0.0,  2.200, 0.785]
PLACE_JOINTS     = [1.57, 0.200, 0.0, -2.000, 0.0,  2.200, 0.785]

def move_to_joints(robot, target_joints, steps=120):
    """
    Smoothly interpolate from the current joint positions to the target.
    'steps' controls how many physics frames the motion takes.
    120 steps ≈ 2 seconds at 60 Hz rendering.
    """
    current = robot.get_joint_positions()
    target  = np.array(target_joints)
    for i in range(steps):
        t = (i + 1) / steps          # goes from 1/steps to 1.0
        interpolated = current + t * (target - current)
        robot.set_joint_positions(interpolated)
        world.step(render=True)      # advance physics + redraw

# ── Execute the pick-and-place sequence ──────────────────
print("Opening gripper...")
robot.gripper.open()
for _ in range(30): world.step(render=True)

print("Moving to pre-grasp (above the cube)...")
move_to_joints(robot, PRE_GRASP_JOINTS)

print("Descending straight down to grasp pose...")
move_to_joints(robot, GRASP_JOINTS)

print("Closing gripper...")
robot.gripper.close()
for _ in range(30): world.step(render=True)

print("Lifting the cube...")
move_to_joints(robot, PRE_GRASP_JOINTS)

print("Transporting to place location...")
move_to_joints(robot, PLACE_JOINTS)

print("Opening gripper to release...")
robot.gripper.open()
for _ in range(30): world.step(render=True)

print("Returning home...")
move_to_joints(robot, HOME_JOINTS)

print("Sequence complete!")

10.6.4 What to Observe

When you run this in Isaac Sim, compare it to the Gazebo version. The motion looks identical in terms of joint angles, but the lighting, shadows, and cube physics will look dramatically more realistic. This comparison makes concrete the trade-off that has been implicit since Chapter 3: Gazebo wins for software integration, Isaac Sim wins for visual fidelity and sensor simulation.

Exercises

  1. Add a VERIFY_GRASP state between GRASP and LIFT. Read the gripper finger positions from /franka_gripper/joint_states and confirm that the gripper did not close past a minimum width (which would indicate it slipped past the object). If the check fails, transition to ERROR.
  2. Replace the hardcoded PICK_POSE with a ROS 2 topic subscriber that receives the object pose from a perception node (or a ROS 2 parameter). Add a new DETECT state at the beginning that waits for the first pose message before advancing.
  3. The transport segment is a single Cartesian straight-line at constant height. In a cluttered scene this might not be collision-free. Replace the transport with an OMPL-planned move (using _plan_to_pose) and add the table and any obstacles to the planning scene. Compare the resulting path to the straight-line.
  4. Wrap the FSM in a ROS 2 action server so that external nodes can trigger a pick-and-place cycle by sending a goal with pick_pose and place_pose fields, and receive feedback after each state transition.
