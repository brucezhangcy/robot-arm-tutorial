Chapter 5

Position Control — Cartesian Space

Chapter 4 moved the arm by saying "put joint 3 at 45°." This chapter is more natural: say "put the gripper at this exact point in space, pointing straight down." MoveIt 2 will figure out what joint angles to use. You will also learn how to make the gripper travel in a perfectly straight line — essential for picking up an object without knocking it sideways.
New terms in this chapter — read these first
Pose
The complete description of where something is: its position (x, y, z in meters) AND its orientation (which way it's pointing). Position alone isn't enough — a screwdriver at the right position but the wrong angle is useless.
SE(3)
The mathematical name for "all possible positions and orientations in 3D space." Every robot pose is one point in SE(3). You don't need to know the math — just know it means "3D position + rotation."
Quaternion
A way to represent rotation using 4 numbers (w, x, y, z) that avoids a problem called "gimbal lock." Computers use quaternions internally; you can convert to/from more intuitive roll/pitch/yaw angles.
Gimbal lock
A problem with 3-angle rotation representations where two axes align and you lose one degree of freedom — the rotation becomes ambiguous. Quaternions avoid this entirely.
Cartesian path
A path where the gripper travels in a mathematically straight line through 3D space. Contrast with a joint-space plan, where the gripper traces whatever arc the joints naturally produce.
Path fraction
A number between 0 and 1 returned by compute_cartesian_path. A fraction of 1.0 means the entire straight-line path is collision-free and ready to execute. Below ~0.95 means part of the path is blocked.
Planning frame
The coordinate frame MoveIt 2 uses when planning. Poses must be expressed in this frame. Usually the robot's base frame (panda_link0).

5.1 Pose Representation in SE(3)

A pose is the combination of a position and an orientation. In robotics, the set of all valid poses of a rigid body in 3D space is written \(SE(3)\) — the Special Euclidean group of dimension three [1]. Every element of \(SE(3)\) can be encoded as a \(4 \times 4\) homogeneous transform matrix:

\[ T = \begin{bmatrix} R & \mathbf{p} \\ \mathbf{0}^\top & 1 \end{bmatrix} \quad R \in SO(3),\quad \mathbf{p} \in \mathbb{R}^3 \]

The \(3 \times 3\) block \(R\) encodes the orientation (rotation relative to some reference frame); the \(3 \times 1\) column \(\mathbf{p} = [x,\, y,\, z]^\top\) encodes the position. You already encountered this matrix in Chapter 2 as the output of forward kinematics. In Cartesian control you use the same matrix as an input: you specify where you want the end-effector to be, and MoveIt 2 finds the joint angles that put it there.

5.2 Representing Orientation

The rotation matrix \(R\) encodes orientation but is awkward to specify by hand — you would need to fill in 9 numbers while satisfying 6 orthogonality constraints. In practice, three more compact representations are used:

RepresentationParametersProsCons / Gotchas
Roll-Pitch-Yaw (RPY) 3 angles: roll \(\phi\), pitch \(\theta\), yaw \(\psi\) Human-readable; easy to reason about in tool frames Gimbal lock at pitch = ±90°; axis order matters (XYZ ≠ ZYX)
Quaternion 4 numbers: \((q_x, q_y, q_z, q_w)\), unit constraint \(|\mathbf{q}|=1\) No gimbal lock; smooth interpolation (SLERP); used internally by MoveIt 2 Non-intuitive; double cover of \(SO(3)\) (\(\mathbf{q}\) and \(-\mathbf{q}\) same rotation)
Axis-Angle Unit axis \(\hat{\mathbf{k}}\) and angle \(\theta\) Geometrically intuitive; easy to construct a specific rotation Singularity at \(\theta = 0\); not directly accepted by MoveIt 2 API

MoveIt 2's Python API accepts a geometry_msgs/Pose message, which stores orientation as a quaternion (x, y, z, w). The helper table below gives quaternions for the most common orientations relative to the robot base frame, saving you from computing them by hand.

Desired EEF orientationQuaternion (x, y, z, w)Notes
Pointing straight down (gripper vertical)(1.0, 0.0, 0.0, 0.0)180° rotation about X; most common pick pose
Pointing straight up(0.0, 0.0, 0.0, 1.0)Identity rotation
Pointing forward (+X axis)(0.707, 0.0, 0.707, 0.0)90° about Y then 90° about X
Rotated 90° about Z from "down"(0.707, 0.707, 0.0, 0.0)Gripper rotated 90° in the horizontal plane
Converting RPY to quaternion in Python: Use transforms3d or scipy:

from scipy.spatial.transform import Rotation as R
q = R.from_euler('xyz', [roll, pitch, yaw]).as_quat() # returns [x, y, z, w]

scipy uses the convention [x, y, z, w] which matches geometry_msgs/Quaternion. Always verify with a sanity-check print before executing on hardware.

5.3 Pose Goals in MoveIt 2

Analogy — Cartesian control as a crane operator: An overhead crane operator doesn't say "rotate the left motor 4.3 revolutions and the right motor 2.1 revolutions." They say "move the hook 2 meters to the left." The crane's internal system figures out which motors to turn by how much. Cartesian control works the same way for the robot arm: you say "put the gripper at position (0.5 m, 0.1 m, 0.3 m) facing downward," and MoveIt 2 uses inverse kinematics to figure out what joint angles achieve that.

Setting a Cartesian pose goal instead of a joint goal requires one extra step internally: MoveIt 2 must run inverse kinematics (IK) to find joint angles \(\mathbf{q}\) that place the end-effector at the desired pose. The planner then plans a collision-free path through joint space to reach those angles, exactly as in Chapter 4. The pipeline is identical — only the way the goal is expressed changes.

The IK solver used by default for the Panda is TRAC-IK, a hybrid analytical/numerical solver that runs in a few milliseconds. If no IK solution exists (the target is outside the workspace or blocked by joint limits), MoveIt 2 returns a planning failure — your code receives False from the plan call and should handle it gracefully.

Multiple IK solutions. For most Cartesian targets the Panda has several valid joint configurations (elbow-up, elbow-down, different wrist orientations). TRAC-IK returns the solution closest to the current joint state. If you need a specific elbow posture, add a joint-space constraint (Chapter 8) or seed the IK solver explicitly.

5.3.1 Specifying a Pose Goal

The key API call is arm.set_goal_state(pose_stamped_msg=…, pose_link=…). The pose_stamped_msg is a geometry_msgs/PoseStamped containing the target pose and the reference frame it is expressed in. The pose_link is the name of the robot link that should reach that pose — typically 'panda_hand' (the EEF flange) or 'panda_EE' (the virtual tool-center-point offset).

5.3.2 Pose vs. Joint Goals — When to Use Each

Use casePreferred goal typeReason
Move to a home or ready position Joint goal Exact joint config known; no IK ambiguity
Place gripper above an object Pose goal You know where the object is, not which joint angles to use
Straight-line approach to a surface Cartesian path (§5.4) Path shape in space matters, not just end point
Scan a flat workpiece Cartesian path EEF must stay at fixed height; joint path would arc away

5.4 Straight-Line Cartesian Paths

A standard pose goal asks MoveIt 2 to reach a target configuration — it doesn't constrain the shape of the path taken through space. The EEF traces whatever arc the joint-interpolated trajectory naturally produces (Figure 5.2, left). When the path shape matters — inserting a connector, wiping a surface, or approaching a pick point along a vertical axis — you need compute_cartesian_path() instead (Figure 5.2, right).

5.4.1 How compute_cartesian_path Works

compute_cartesian_path() interpolates the end-effector linearly between consecutive waypoints in Cartesian space. At each interpolation step (controlled by the max_step parameter, in meters) it calls the IK solver to find joint angles that place the EEF at that interpolated position. The result is a joint trajectory that, when executed, keeps the EEF on the straight line.

The function returns two values: the planned trajectory and a fraction (0.0–1.0) indicating what percentage of the requested path was successfully planned. A fraction below 1.0 means the arm ran out of reachable space or hit a collision along the path. Always check the fraction before executing:

Always check the fraction. If fraction < 0.95, the arm will stop mid-path. On real hardware this can leave the arm at an awkward intermediate pose. Design waypoint sequences that stay within the workspace, and add a minimum-fraction check before calling execute().

5.4.2 Choosing max_step

The max_step parameter (default ~5 mm) controls how finely the Cartesian path is interpolated. Smaller values produce smoother motion but require more IK calls and more waypoints in the trajectory. In practice:

  • 5 mm (0.005) — good general default; smooth motion, fast planning
  • 1 mm (0.001) — high-precision tasks (PCB probing, connector insertion)
  • 10 mm (0.01) — fast rough scans where path smoothness is less critical

5.5 Reference Frames

Every pose goal must be expressed relative to a specific frame. Specifying a pose in the wrong frame is one of the most common bugs in Cartesian control — the numbers look right but the robot moves to the wrong place. Figure 5.3 shows the three frames you will use most often.

5.5.1 Planning Frame vs. EEF Link

Two frame concepts are easy to confuse:

Planning frame (frame_id in the PoseStamped)
The coordinate system your target \(x, y, z\) coordinates are measured in. Almost always 'panda_link0' (the robot base). If you use 'world' instead and the robot is not at the world origin, your coordinates will be wrong.
EEF link (pose_link in the API call)
The link on the robot that should arrive at the target pose. Use 'panda_hand' for the flange, or 'panda_EE' if you need to account for an attached tool's extra length.
On real hardware (Chapter 9), the world frame coincides with panda_link0 if the robot is fixed — the static transform between them is set to identity. This means the same Python code works in simulation and on hardware as long as you use 'panda_link0' as your reference frame.

5.6 Code Examples

5.6.1 Move to a Cartesian Pose Goal

This script moves the EEF to a specified position and orientation in the panda_link0 frame. MoveIt 2 solves IK internally, plans a collision-free joint path, and executes it.

move_to_pose.py
#!/usr/bin/env python3
"""
Move the Panda end-effector to a target Cartesian pose via MoveIt 2.
IK is solved internally by TRAC-IK; the planner finds a collision-free
joint path to the resulting configuration.

Requires: simulation running (ch03 launch_sim.sh).
"""

import rclpy
from rclpy.node import Node
from moveit.planning import MoveItPy
from geometry_msgs.msg import Pose, PoseStamped


class PoseGoalClient(Node):
    def __init__(self):
        super().__init__('pose_goal_client')
        self.moveit = MoveItPy(node_name='pose_goal_moveit')
        self.arm = self.moveit.get_planning_component('panda_arm')
        self.get_logger().info('MoveIt 2 initialized.')

    def move_to_pose(
        self,
        x: float, y: float, z: float,
        qx: float, qy: float, qz: float, qw: float,
        vel_scale: float = 0.3,
    ) -> bool:
        """
        Plan and execute a move to a Cartesian pose.

        Args:
            x, y, z:         EEF target position in panda_link0 frame (meters)
            qx, qy, qz, qw:  EEF target orientation as a unit quaternion
            vel_scale:        velocity scaling factor (0.0 – 1.0)

        Returns:
            True on success, False on planning or execution failure.
        """
        target = PoseStamped()
        target.header.frame_id = 'panda_link0'
        target.pose.position.x = x
        target.pose.position.y = y
        target.pose.position.z = z
        target.pose.orientation.x = qx
        target.pose.orientation.y = qy
        target.pose.orientation.z = qz
        target.pose.orientation.w = qw

        self.arm.set_start_state_to_current_state()
        self.arm.set_goal_state(
            pose_stamped_msg=target,
            pose_link='panda_hand',
        )

        plan = self.arm.plan(
            single_plan_parameters={
                'max_velocity_scaling_factor': vel_scale,
                'max_acceleration_scaling_factor': vel_scale,
            }
        )
        if not plan:
            self.get_logger().error(
                'Planning failed — target may be unreachable or in collision.'
            )
            return False

        result = self.moveit.execute(plan.trajectory, controllers=[])
        if not result:
            self.get_logger().error('Execution failed.')
            return False

        self.get_logger().info('Pose goal reached.')
        return True


def main():
    rclpy.init()
    client = PoseGoalClient()

    # Move to a position 40 cm in front of and 40 cm above the base,
    # gripper pointing straight down (180-degree rotation about X).
    success = client.move_to_pose(
        x=0.4, y=0.0, z=0.4,
        qx=1.0, qy=0.0, qz=0.0, qw=0.0,
        vel_scale=0.3,
    )
    print('Success:', success)
    rclpy.shutdown()


if __name__ == '__main__':
    main()

5.6.2 Straight-Line Cartesian Path

This script plans a straight-line sweep of the EEF along the X axis. Each entry in waypoints is a Pose that the EEF passes through; compute_cartesian_path() interpolates between them and returns the planned fraction.

cartesian_path.py
#!/usr/bin/env python3
"""
Plan and execute a straight-line Cartesian path through a list of waypoints.

Uses compute_cartesian_path() which ensures the EEF moves in a straight line
in Cartesian space — not just in joint space. Always check the returned fraction
before executing; a fraction below 1.0 means part of the path was unreachable.

Use cases:
  - Wiping or scanning a flat surface
  - Straight approach to a pick/place point
  - Drawing a line or rectangle in space
"""

import rclpy
from rclpy.node import Node
from moveit.planning import MoveItPy
from geometry_msgs.msg import Pose

MIN_FRACTION = 0.95   # Abort if less than 95% of path was planned


class CartesianPathClient(Node):
    def __init__(self):
        super().__init__('cartesian_path_client')
        self.moveit = MoveItPy(node_name='cartesian_path_moveit')
        self.arm = self.moveit.get_planning_component('panda_arm')

    @staticmethod
    def make_pose(x, y, z, qx=1.0, qy=0.0, qz=0.0, qw=0.0) -> Pose:
        """Build a Pose message from position and quaternion."""
        p = Pose()
        p.position.x = x
        p.position.y = y
        p.position.z = z
        p.orientation.x = qx
        p.orientation.y = qy
        p.orientation.z = qz
        p.orientation.w = qw
        return p

    def run_cartesian_path(
        self,
        waypoints: list[Pose],
        max_step: float = 0.005,
        vel_scale: float = 0.2,
    ) -> bool:
        """
        Plan and execute a Cartesian path through the given waypoints.

        Args:
            waypoints:    EEF poses in panda_link0 frame; path is interpolated between them
            max_step:     maximum Cartesian interpolation distance in meters (default 5 mm)
            vel_scale:    velocity scaling factor applied to the resulting trajectory

        Returns:
            True on success.
        """
        self.arm.set_start_state_to_current_state()

        plan, fraction = self.arm.compute_cartesian_path(
            waypoints=waypoints,
            max_step=max_step,
            jump_threshold=0.0,    # 0 disables joint-space jump detection
        )

        self.get_logger().info(f'Cartesian path fraction: {fraction * 100:.1f}%')

        if fraction < MIN_FRACTION:
            self.get_logger().error(
                f'Only {fraction * 100:.0f}% of path reachable — aborting.'
            )
            return False

        result = self.moveit.execute(plan.trajectory, controllers=[])
        return bool(result)


def main():
    rclpy.init()
    client = CartesianPathClient()

    # Sweep the EEF 20 cm along the X axis at fixed height and Y position.
    # All poses: gripper pointing down (qx=1, qw=0).
    waypoints = [
        client.make_pose(x=0.30, y=0.0, z=0.40),
        client.make_pose(x=0.35, y=0.0, z=0.40),
        client.make_pose(x=0.40, y=0.0, z=0.40),
        client.make_pose(x=0.45, y=0.0, z=0.40),
        client.make_pose(x=0.50, y=0.0, z=0.40),
    ]

    success = client.run_cartesian_path(waypoints, max_step=0.005, vel_scale=0.2)
    print('Success:', success)
    rclpy.shutdown()


if __name__ == '__main__':
    main()
Combining pose goals and Cartesian paths: A common pattern is to use a joint goal (Chapter 4) or pose goal to position the arm in a general area, then switch to a Cartesian path for the final precision approach. This avoids planning failures that occur when compute_cartesian_path() is called from a poor starting configuration.
Chapter 5 Summary — What you learned:
  • SE(3) is just the mathematical name for "a position in 3D + an orientation." Every robot pose — where the gripper is and which way it's pointing — lives in SE(3).
  • Quaternions represent orientation as 4 numbers instead of 3 Euler angles; they avoid "gimbal lock" (a situation where two rotation axes align and you lose one degree of freedom) and blend smoothly for interpolation.
  • For a straight-line path (like descending vertically onto a part), use compute_cartesian_path() — it guarantees the gripper travels in a straight line in 3D, which a joint-space plan does not.
  • Always check the fraction returned: if it is below ~0.95, part of the straight line is blocked and you should adjust the scene or approach direction before executing.

  2. Modify cartesian_path.py to draw a square: four waypoints forming a 20 cm × 20 cm square in the XY plane at Z = 0.4 m. Add a fifth waypoint that returns to the start. What fraction do you achieve?

Key Terms — Chapter 5

SE(3)
The Special Euclidean group — the mathematical set of all 3D poses (position + orientation).
Pose
A position (x, y, z in meters) combined with an orientation (rotation); fully describes where a frame is in space.
Quaternion
A 4-number representation of orientation (x, y, z, w) with no gimbal lock; used internally by MoveIt 2.
Roll-Pitch-Yaw (RPY)
Three Euler angles describing successive rotations; intuitive but order-dependent and susceptible to gimbal lock.
Pose goal
A Cartesian target pose for the EEF; MoveIt 2 solves IK to find the required joint angles.
compute_cartesian_path
MoveIt 2 API that interpolates the EEF in straight lines between waypoints and returns a trajectory fraction.
Path fraction
The portion (0–1) of a requested Cartesian path that was successfully planned; values below 1 indicate unreachable segments.
panda_link0
The robot base frame; use as the reference for all Cartesian pose coordinates in Python code.
panda_hand
The EEF flange link; use as pose_link when specifying which link should reach the target pose.
panda_EE
A virtual tool-center-point frame 107 mm beyond the flange; useful when a tool extends the physical reach.
TRAC-IK
The default inverse kinematics solver in MoveIt 2; returns the IK solution closest to the current joint state.
