Chapter 1

Foundations & Toolchain

A robot arm is a machine that can pick up, move, and place objects — just like a human arm, but programmable. This chapter introduces the specific arm we use (the Franka Panda), the software that makes it work, and how to get everything installed on your computer. No robotics background required. If you know a little Python and can use a terminal, you are ready to start.

Key Terms — Chapter 1

Robot arm
A mechanical arm made of motors and rigid pieces that can be programmed to move to any position.
Joint
A motor-driven connection between two rigid pieces of the arm. Each joint adds one direction of movement (rotation). Think of your elbow or shoulder.
Link
One of the rigid pieces between joints — like the bones in your arm.
DOF
Degree of Freedom — the number of independent directions something can move. The Panda has 7 joints, so 7 DOF.
Revolute joint
A joint that rotates about a single fixed axis.
Torque
A rotational force — the force used to turn a bolt with a wrench. Measured in Newton-meters (N·m).
End-effector (EEF)
The "hand" at the very tip of the arm — often a gripper that can open and close to pick up objects.
ROS 2
An open-source software framework that robot programs use to talk to each other. Like an operating system, but specifically for robots.
Node
An independent ROS 2 process that does one specific job and communicates via topics, services, or actions.
Topic
A named, one-directional data stream in ROS 2. Nodes publish data to a topic; other nodes subscribe to receive it.
Action
A ROS 2 interface for long-running tasks with goal, feedback, and result.
FCI
Franka Control Interface — the low-level 1 kHz Ethernet protocol between a PC and the Panda arm.
libfranka
Franka's official C++ library that wraps the FCI protocol.
MoveIt 2
The ROS 2 motion planning framework used throughout this tutorial.
Torque sensor
Measures the rotational force at a joint; enables compliance and safety reflexes.
Gazebo
A physics-based robot simulator. Simulates the arm on your computer so you can test code safely before touching real hardware.
Isaac Sim
NVIDIA's photorealistic robot simulator. Uses a GPU to render camera images that look like real photographs — important for training AI vision models.
Docker
A tool that packages a complete Linux environment — with all software pre-installed — into a self-contained "container" that runs on any computer. Used in this tutorial so macOS and Windows users can run ROS 2 without a separate Linux machine.
Container
A lightweight, isolated environment created by Docker. Like a mini-PC running inside your laptop: it has its own operating system and installed packages, but shares your files and screen.

1.1 The Franka Emika Panda

The Franka Emika Panda is a 7-degree-of-freedom (7-DOF) collaborative robot arm designed for research and industrial tasks that require close interaction with people [1]. It is manufactured by Franka Robotics GmbH (formerly Franka Emika GmbH) and is widely used in university robotics labs worldwide. We chose it for this tutorial because it combines cutting-edge hardware with excellent open-source software support — a rare combination in robotics.

What sets the Panda apart from earlier industrial arms is its joint-level torque sensing. Every one of its seven joints contains a high-resolution torque sensor that measures the force being applied at that joint 1,000 times per second. This allows the robot to detect unexpected contact, respond compliantly to human touch, and execute delicate manipulation tasks that would be impossible with a rigid position-controlled arm. That torque sensing is also why the advanced control modes in Chapter 7 are even possible.

1.1.1 Physical Anatomy

The arm consists of seven revolute joints (joints that rotate around a single axis) connected by rigid aluminum links. At the very tip of the arm is the end-effector (abbreviated EEF) — the mounting flange where a tool such as a gripper, camera, or suction cup attaches to interact with objects in the world. The arm's entire job is to move and orient that flange precisely. Figure 1.1 shows the full anatomy.

1.1.2 Key Specifications

The Panda's torque sensors, combined with its 7th redundant degree of freedom, are what enable the advanced control modes covered later in this tutorial (Chapter 7). Table 1.1 summarizes the key specifications [2].

PropertyValue

What is a DOF? A degree of freedom (DOF) is an independent direction of motion. A revolute joint adds one rotational DOF. A free-flying object in 3D space has 6 DOF (3 translational + 3 rotational). The Panda has 7 DOF — one more than the minimum needed to reach any pose in its workspace — making it kinematically redundant. Chapter 2 explains how this redundancy is exploited.

1.2 ROS 2 Overview

ROS 2 (Robot Operating System 2) is an open-source middleware framework for building robot software [3]. Despite the name, it is not an operating system — it runs on top of Linux (or Windows/macOS). Think of it as a standardized communication bus that lets separate programs — called nodes — talk to each other as if they were one integrated application. Every piece of software in this tutorial is a ROS 2 node.

Without ROS 2, you would need to write custom networking code every time two parts of your robot software needed to share data. With ROS 2, a sensor driver, a motion planner, a visualizer, and your control code can all run as independent processes and exchange data through a well-defined API. This is the foundation on which MoveIt 2 (Chapter 8) and the simulation environment (Chapter 3) are both built.

Analogy — ROS 2 as a group chat: Think of ROS 2 like the messaging apps on your phone. Each app (camera, maps, music player) runs independently, but they all share data through the phone's notification system. In ROS 2, each node is like one app: the camera node streams images, the planner node figures out paths, and the controller node moves the joints — none of them need to know how the others work internally. If you had to wire all of this together by hand with custom networking code, you would spend months on plumbing before you could move a single joint.

1.2.1 Core Concepts

ROS 2 organizes communication into four primitives:

  • Node — an independent process (usually one Python or C++ program) that does one job: read a camera, plan a trajectory, publish a control command, etc.
  • Topic — a named data stream. Nodes publish messages to a topic; other nodes subscribe to receive them. Topics are one-directional and continuous (e.g., /joint_states publishes the arm's current position at 1 kHz).
  • Service — a request–response interaction. One node calls a service with a request; the server node responds once (e.g., "add this collision object to the planning scene").
  • Action — like a service, but for long-running tasks. An action sends a goal, streams periodic feedback while executing, and returns a final result. MoveIt 2 exposes its motion planning as an action (e.g., "move to this joint configuration").

Figure 1.2 shows these three primitives side by side. Mastering them is the prerequisite to reading any ROS 2 node graph — and you will see all three in action throughout this tutorial.

1.2.2 The ROS 2 Node Graph

When the full Panda simulation is running, several nodes are active simultaneously. Figure 1.3 shows the major nodes and how they communicate for our tutorial setup.

Key insight: You never write code that directly drives the robot's motors. Your Python node sends a high-level goal ("move to this pose") to move_group, which plans a safe trajectory, then commands the hardware through the controller manager. This layered architecture is what makes the same code work in both simulation and on real hardware.

1.3 The Full Software Stack

Between your Python code and the physical motors are several layers of software. Each layer provides an abstraction: you write a goal in terms of "meters and radians," and the layers below translate that into motor currents at 1 kHz. This is powerful because you never have to think about raw motor signals — but it does mean that when something goes wrong, you need to know which layer is responsible. Figure 1.4 shows these layers from top to bottom.

Layer Descriptions

libfranka / FCI
Franka's official C++ library for real-time robot control [4]. It communicates with the robot over a 1 Gbps Ethernet link at 1 kHz and implements the robot's built-in safety reflexes (automatic stops when unexpected forces are detected). You almost never call this directly; franka_ros2 wraps it.
franka_ros2 Hardware Interface
A ROS 2 package that translates between the ros2_control API and libfranka. It reads joint positions, velocities, and torques from the robot and writes commanded torques back. In simulation, a Gazebo plugin plays this role.
ros2_control / controller_manager
Manages a set of controllers — algorithms that take a trajectory goal and produce motor commands at the required frequency. We will use the JointTrajectoryController (Chapters 4–5), JointVelocityController (Chapter 6), and the impedance controller (Chapter 7).
ROS 2 Middleware
Built on DDS (Data Distribution Service), a real-time publish–subscribe standard [3]. Handles discovery, serialization, and delivery of messages between all nodes on the network.
MoveIt 2
The primary motion planning framework in ROS 2 [5]. Given a goal pose (the desired position and orientation of the end-effector) or joint configuration, MoveIt 2 runs a sampling-based planner (Chapter 8), checks the trajectory for collisions, and sends it to the controller manager.
Your Python Code
Calls the MoveGroupInterface Python API to set goals, trigger planning, and execute trajectories. This is what all of the code examples in this tutorial are written in.
What about Isaac Sim? Isaac Sim (by NVIDIA) is a second simulator worth knowing about. Unlike Gazebo — which focuses on accurate physics — Isaac Sim renders photorealistic camera images using a GPU ray-tracer. That makes it essential when training AI models to recognise objects: the synthetic training photos need to look like real photographs. For the motion-planning and control topics in Chapters 1–9, Gazebo is simpler, faster to start, and works without a GPU. Chapter 10 §10.6 includes a hands-on Isaac Sim bonus project.

1.4 Installation

What is Docker?

Imagine you could carry a complete Ubuntu Linux laptop — with ROS 2, Gazebo, MoveIt 2, and every package already installed — inside a single file on your Mac or Windows PC. That is essentially what Docker does.

Docker creates a container: a sealed, lightweight copy of Ubuntu that runs as a normal process on your computer. From inside the container, everything looks and behaves like a real Ubuntu machine. From outside, it is just an app — you can start it, stop it, and throw it away without touching your real operating system.

Why does that matter? ROS 2 is officially supported only on Ubuntu 22.04. Without Docker, macOS and Windows users would need a separate Linux computer or a complex dual-boot setup. With Docker, you run the full ROS 2 stack on any laptop in about five minutes.

Key things to know before you start:

  • Your files on your Mac/PC are shared into the container — edits you make inside Docker are immediately visible outside, and vice versa.
  • When you exit the container, everything you installed inside it is gone (unless you save a snapshot). Your code files are safe because they live on your real computer.
  • Graphical apps (Gazebo, RViz) can appear on your Mac screen using an X11 server called XQuartz — the steps below set that up for you.

This tutorial requires Ubuntu 22.04 LTS with ROS 2 Humble to run the full simulation (Gazebo, RViz, MoveIt 2). Read the platform guide below carefully before starting — your choice of computer affects what you can run.

Platform requirements — read this first:
Platform Python code Gazebo / RViz GUI Real hardware (ch09)
Ubuntu 22.04 (native or VM with GPU) ✅ ✅ Full support ✅ (bare-metal only)
macOS Apple Silicon (M1/M2/M3) + Docker ✅ ❌ OpenGL blocked ❌
macOS Intel + Docker + XQuartz ✅ ⚠️ Requires extra setup ❌

Bottom line: Ubuntu 22.04 is the only platform where every chapter works without workarounds. On a Mac, you can read code, run Python files, and use ROS 2 nodes — but you cannot see the robot moving in Gazebo or RViz, which is central to Chapters 3–10.

If you only have a Mac, the most practical paths are:
  • UTM or Parallels — run a free Ubuntu 22.04 arm64 VM with GPU passthrough. Gazebo and RViz work inside the VM.
  • Cloud Ubuntu VM (AWS, GCP, DigitalOcean) — SSH in with -X flag or use a VNC desktop. Free-tier machines are sufficient for Chapters 2–8.
  • Docker (code-only) — use Option A below to run and test Python code, but skip the Gazebo visualization steps until you have access to Ubuntu.
Which option should I choose?
  • Ubuntu 22.04 natively → Option B. This is the recommended path — everything works out of the box.
  • macOS or Windows → Option A (Docker) for code development and headless ROS 2 usage. See the warning above for GUI limitations.

Option A — Docker (code development · macOS · Windows)

A1 — Install Docker Desktop

Docker Desktop is a free application that runs containers on your computer.

bash — macOS (Homebrew, easiest)
brew install --cask docker

Then open Docker Desktop from your Applications folder and wait for the whale icon in your menu bar to stop animating — that means Docker is ready.

No Homebrew? Download Docker Desktop directly from docker.com/products/docker-desktop → click the button for your chip (Apple Silicon or Intel) → open the downloaded .dmg and drag Docker to Applications.

A2 — Install XQuartz (macOS only — needed for Gazebo GUI)

XQuartz lets graphical apps running inside Docker show their windows on your Mac screen. Without it, Gazebo's 3D view will not appear.

bash — macOS
brew install --cask xquartz

After installation, log out and log back in (or restart) so XQuartz becomes the default X11 server. Then open XQuartz from Applications → Utilities, go to Preferences → Security, and check "Allow connections from network clients".

A3 — Pull the ROS 2 Humble image

This downloads about 2 GB — do it once on a fast connection.

bash — any terminal
docker pull osrf/ros:humble-desktop

A4 — Start the container (run this every session)

bash — macOS
# Allow Docker to open windows on your screen
xhost +localhost

# Start the ROS 2 container
# - your current folder is mounted at /workspace inside the container
# - GUI windows (Gazebo, RViz) will appear on your Mac screen
docker run -it --rm \
    --name ros2_tutorial \
    -e DISPLAY=host.docker.internal:0 \
    -e LIBGL_ALWAYS_INDIRECT=0 \
    -v /tmp/.X11-unix:/tmp/.X11-unix \
    -v "$(pwd)":/workspace \
    -w /workspace \
    osrf/ros:humble-desktop bash

You are now inside a Ubuntu 22.04 shell with ROS 2 Humble ready. Your files in the current folder appear at /workspace inside the container.

A5 — Inside the container: install MoveIt 2 and Franka packages

Run these once inside a fresh container (skip if you already built a custom image).

bash — inside the Docker container
source /opt/ros/humble/setup.bash

sudo apt update && sudo apt install -y \
    ros-humble-moveit \
    ros-humble-franka-description \
    ros-humble-franka-msgs \
    ros-humble-gazebo-ros2-control \
    ros-humble-ros2-control \
    ros-humble-ros2-controllers \
    python3-rosdep

# Initialize rosdep (skip if already done)
sudo rosdep init 2>/dev/null || true
rosdep update

# Clone and build franka_ros2
mkdir -p /workspace/panda_ws/src && cd /workspace/panda_ws/src
git clone https://github.com/frankaemika/franka_ros2.git --branch humble
cd /workspace/panda_ws
rosdep install --from-paths src --ignore-src -r -y
colcon build --symlink-install --cmake-args -DCMAKE_BUILD_TYPE=Release

# Source everything
source /opt/ros/humble/setup.bash
source /workspace/panda_ws/install/setup.bash
Tip — save your work across sessions: The container is deleted when you exit (--rm flag). Your code in /workspace is safe because it is mounted from your Mac. Re-run A5 after pulling the image, or build a custom image with docker commit to avoid reinstalling each time.
Apple Silicon (M1/M2/M3) Mac — known limitation with RViz and Gazebo GUI: The official ROS 2 Docker image (osrf/ros:humble-desktop) is only built for x86-64 (amd64). On Apple Silicon Macs, Docker Desktop runs it through Rosetta 2 emulation inside a virtual machine. That VM has no access to the Mac GPU, so RViz 2 and Gazebo cannot create a hardware-accelerated OpenGL window — they crash with a GLXContext error even with XQuartz set up correctly.

What still works on Apple Silicon: All Python code runs correctly inside the container (syntax, imports, ROS 2 nodes, MoveIt 2 planning). Only the 3D GUI tools (RViz, Gazebo viewer) are blocked.

Workarounds:
  • UTM or Parallels with Ubuntu 22.04 VM (recommended) — a native arm64 Ubuntu VM with hardware GPU passthrough can run RViz and Gazebo normally.
  • Intel Mac — Docker + XQuartz works without this limitation.
  • Remote Ubuntu machine — run the tutorial on any Ubuntu 22.04 PC and SSH with X11 forwarding (ssh -X user@host).

A6 — Launch the Panda simulation (inside the container)

Package name change (franka_ros2 ≥ 2024): The franka_ros2 Humble branch was refactored to target the newer Franka Research 3 (FR3) robot. The old franka_gazebo and panda_moveit_config packages no longer exist. Use robot_type:=fer to select the classic Panda (FER = Franka Emika Robot) model.
bash — inside the Docker container
source /opt/ros/humble/setup.bash
source /workspace/panda_ws/install/setup.bash

# Terminal 1 — start Gazebo with the Panda arm
# robot_type:=fer selects the classic Panda (Franka Emika Robot)
ros2 launch franka_gazebo_bringup gazebo_franka_arm_example_controller.launch.py robot_type:=fer

# Open a second terminal in the same container:
#   docker exec -it ros2_tutorial bash
# Then in Terminal 2 — start MoveIt 2
source /opt/ros/humble/setup.bash && source /workspace/panda_ws/install/setup.bash
ros2 launch franka_fr3_moveit_config move_group.launch.py

Option B — Native Ubuntu 22.04

If you are running Ubuntu 22.04 natively or in a VM, follow Steps 1–3 in order.

Warning: Do not install ROS 2 inside a conda or virtual environment. ROS 2 modifies system Python paths in ways that conflict with environment managers. Use the system Python provided by ROS 2.

Step 1 — Install ROS 2 Humble (Ubuntu native only)

bash

1.5 Verifying Your Installation

Before writing any robot code, it is worth spending two minutes confirming that everything is correctly installed. Run the script below to check every required package. A passing run prints ✓ for each check; a failing run prints the exact missing package so you know what to fix.

verify_install.sh
#!/usr/bin/env bash
# Verify all required packages for the Panda tutorial are installed.
set -euo pipefail

PASS="✓"
FAIL="✗"
errors=0

check_pkg() {
    local pkg="$1"
    if dpkg -s "$pkg" &>/dev/null; then
        echo "$PASS  $pkg"
    else
        echo "$FAIL  $pkg  (not installed)"
        errors=$((errors + 1))
    fi
}

check_python() {
    local mod="$1"
    if python3 -c "import $mod" &>/dev/null; then
        echo "$PASS  python3.$mod"
    else
        echo "$FAIL  python3.$mod  (import failed)"
        errors=$((errors + 1))
    fi
}

check_ros_pkg() {
    local pkg="$1"
    if ros2 pkg list 2>/dev/null | grep -q "^${pkg}$"; then
        echo "$PASS  ros2 pkg: $pkg"
    else
        echo "$FAIL  ros2 pkg: $pkg  (not found)"
        errors=$((errors + 1))
    fi
}

echo "=== System packages ==="
check_pkg ros-humble-desktop
check_pkg ros-humble-moveit
check_pkg ros-humble-ros2-control
check_pkg ros-humble-ros2-controllers

echo ""
echo "=== Python modules ==="
check_python rclpy
check_python moveit
check_python numpy

echo ""
echo "=== ROS 2 packages ==="
check_ros_pkg franka_description
check_ros_pkg franka_msgs
check_ros_pkg moveit_ros_planning_interface

echo ""
if [ $errors -eq 0 ]; then
    echo "All checks passed. Your environment is ready."
else
    echo "$errors check(s) failed. See above for details."
    exit 1
fi

Next, confirm that ROS 2 itself is working by running a minimal node:

minimal_ros2_node.py
#!/usr/bin/env python3
"""Minimal ROS 2 node — confirms rclpy is installed and DDS communication works."""

import rclpy
from rclpy.node import Node


class MinimalNode(Node):
    def __init__(self):
        super().__init__('minimal_node')
        self.get_logger().info('Node is running. ROS 2 environment is correctly set up.')
        # Publish one message then exit
        timer = self.create_timer(0.1, self._on_timer)
        self._timer = timer

    def _on_timer(self):
        self.get_logger().info('Timer fired — spinning correctly.')
        self._timer.cancel()
        rclpy.shutdown()


def main():
    rclpy.init()
    node = MinimalNode()
    rclpy.spin(node)


if __name__ == '__main__':
    main()

Run it with:

bash
python3 minimal_ros2_node.py

You should see two log lines and the process should exit cleanly. If you see rclpy not found, your ROS 2 environment is not sourced — run source /opt/ros/humble/setup.bash first. Once this test passes, you are ready for Chapter 2, where we will explore the mathematics that let the arm know where it is in space.

Chapter 1 Summary
  • The Franka Panda is a 7-DOF collaborative robot arm with torque sensors at every joint. Those sensors are what make it safe near people and capable of detecting unexpected contact — not just blindly following position commands like a classical industrial robot.
  • Your code never talks directly to the motors. A layered software stack handles each level of abstraction: your Python code sets goals → MoveIt 2 plans a collision-free path → ros2_control runs 1 kHz PID loops → franka_ros2 sends commands over Ethernet → joints move. Understanding which layer does what is the key to debugging the whole system.
  • ROS 2 is the communication backbone connecting every layer: independent programs called nodes exchange data via Topics (continuous streams), Services (single request/reply), and Actions (long tasks with progress updates). Knowing which of the three to use is a core ROS 2 skill you will apply in every subsequent chapter.
  • Always develop in simulation first. Gazebo is the physics simulator used in Chapters 1–9; Isaac Sim (Chapter 10 §10.6) adds photorealistic GPU rendering for AI vision training. Never run untested code on real hardware.
  • Ubuntu 22.04 is the only platform where every chapter works without workarounds. On macOS (especially Apple Silicon), Docker lets you run Python code and ROS 2 nodes, but the Gazebo and RViz 3D GUI cannot render — a hardware OpenGL limitation. The most practical Mac path is a Ubuntu 22.04 VM (UTM/Parallels) or a cloud Ubuntu machine.

Exercises

  1. Run ros2 topic list while the Panda URDF is loaded in RViz. How many topics are published? Identify the topic that carries joint positions and its message type. (Hint: ros2 topic info /joint_states)
  2. The Panda has 7 DOF, but a rigid body in 3D space requires only 6 DOF (3 translation + 3 rotation) to reach any pose. What is the extra DOF used for? Research the term "null-space motion" and write a one-paragraph explanation in your own words.
  3. Modify minimal_ros2_node.py to publish a std_msgs/String message to a topic called /hello_robot every 0.5 seconds. In a second terminal, subscribe to that topic with ros2 topic echo /hello_robot and confirm you see the messages. (Reference: Appendix A)
