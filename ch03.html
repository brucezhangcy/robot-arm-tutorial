Chapter 3

The Simulation Environment

Before touching real hardware, every motion should be tested in simulation. This chapter explains the three simulation components — Gazebo, RViz, and MoveIt 2 — how they communicate, and how to launch them together for the Panda. You will learn to inspect the TF tree, verify controller loading, and confirm that your development environment exactly mirrors what runs on real hardware.

3.1 Simulation Component Overview

Three programs form the simulation stack. Each does a distinct job; understanding their boundaries prevents confusion when something goes wrong.

  • Gazebo — a physics engine. It simulates motor dynamics, gravity, inertia, and contact forces. From ROS 2's perspective it appears as a hardware interface that publishes /joint_states and accepts joint commands.
  • RViz — a 3D visualization tool. It does not simulate physics; it only renders what it reads from ROS 2 topics (joint states, TF frames, planning scenes). Running RViz without Gazebo shows the robot "frozen" at its initial pose.
  • MoveIt 2 — the motion planning framework (move_group node). It is physics-agnostic; it plans trajectories and sends them to whatever controller manager is active — Gazebo in simulation, the real FCI on hardware.

3.2 The URDF and XACRO Model

The Unified Robot Description Format (URDF) is an XML file that describes the robot's geometry, inertial properties, and joint limits [1]. For the Panda, the URDF is split into several XACRO (XML macro) files that are assembled at launch time. Figure 3.2 shows the include hierarchy.

Key URDF Concepts

The URDF encodes the robot as a kinematic tree of alternating <link> and <joint> elements:

panda.urdf (excerpt — one link/joint pair)
<link name="panda_link2">
  <inertial>
    <mass value="2.7426"/>
    <inertia ixx="7.0337e-3" iyy="7.0661e-3" izz="1.2805e-3" .../>
  </inertial>
  <visual><geometry><mesh filename="meshes/visual/link2.dae"/></geometry></visual>
  <collision><geometry><mesh filename="meshes/collision/link2.stl"/></geometry></collision>
</link>

<joint name="panda_joint2" type="revolute">
  <parent link="panda_link1"/>
  <child  link="panda_link2"/>
  <origin xyz="0 0 0" rpy="-1.5708 0 0"/>  <!-- DH alpha_2 = -pi/2 -->
  <axis xyz="0 0 1"/>
  <limit lower="-1.7628" upper="1.7628" velocity="1.4835" effort="87"/>
</joint>

3.3 The TF Tree

The TF2 library maintains a tree of coordinate frame transforms that any node can query at any time [2]. For the Panda, robot_state_publisher continuously publishes the transform from each link to its parent based on the current /joint_states. Figure 3.3 shows the full Panda TF tree.

3.4 The Controller Manager

The controller_manager node loads, configures, and activates controllers. Each controller has a lifecycle state machine with four states, shown in Figure 3.4. Only one controller can be active per hardware interface at a time — switching from position to impedance control means deactivating the position controller first.

3.5 Launching the Simulation

The following scripts launch the complete simulation stack and provide diagnostic commands to verify every component is running correctly.

launch_sim.sh — Launch Gazebo + RViz + MoveIt 2
#!/usr/bin/env bash
# Launch the full Panda simulation stack.
# Run this in a dedicated terminal; it stays open.

source /opt/ros/humble/setup.bash
source ~/panda_ws/install/setup.bash

ros2 launch franka_moveit_config moveit.launch.py \
    robot_ip:=dont_need_it \
    use_fake_hardware:=true \
    fake_sensor_commands:=true

# What each argument does:
#   robot_ip:=dont_need_it     → placeholder (not used in simulation)
#   use_fake_hardware:=true    → load Gazebo/fake hardware interface instead of FCI
#   fake_sensor_commands:=true → allow setting joint states via service for testing
inspect_tf.sh — Dump TF tree to a PDF
#!/usr/bin/env bash
# Dump the running TF tree to frames.pdf (requires graphviz)
source /opt/ros/humble/setup.bash

ros2 run tf2_tools view_frames &
sleep 3
kill %1 2>/dev/null

echo "TF tree saved to frames.pdf"
echo ""
echo "--- Static transforms ---"
ros2 topic echo /tf_static --once

echo ""
echo "--- Dynamic transforms (first message) ---"
ros2 topic echo /tf --once | head -50
list_controllers.sh — Verify controllers are active
#!/usr/bin/env bash
source /opt/ros/humble/setup.bash

echo "=== Active controllers ==="
ros2 control list_controllers

echo ""
echo "=== Hardware interfaces ==="
ros2 control list_hardware_interfaces

echo ""
echo "=== Hardware components ==="
ros2 control list_hardware_components

# Expected output (sim):
# [active] joint_state_broadcaster/JointStateBroadcaster
# [active] panda_arm_controller/JointTrajectoryController
# [active] panda_hand_controller/GripperActionController
Tip: Open three terminals: one for the launch file, one for RViz (which opens automatically), and one for diagnostic commands. Never kill the launch terminal while controllers are active — it can leave the ros2_control state machine in an inconsistent state requiring a full restart.

Exercises

  1. Launch the simulation and run ros2 topic list | grep -v param. How many topics are published? Identify the topic that carries gripper state.
  2. Run inspect_tf.sh and open frames.pdf. How many frames are in the tree? What is the parent of panda_link4?
  3. Run list_controllers.sh. Are the three expected controllers active? What happens if you run ros2 control switch_controllers --deactivate panda_arm_controller? Can you reactivate it?

Key Terms — Chapter 3

Gazebo
A physics-based robot simulator that publishes joint states and accepts joint commands.
RViz
A 3D visualization tool; reads topics but has no physics.
URDF
XML format describing robot geometry, inertia, and joint limits.
XACRO
An XML macro system used to modularize URDF files.
TF2
ROS 2 library that maintains a tree of time-stamped coordinate transforms.
controller_manager
Manages the lifecycle (load, configure, activate, deactivate) of ros2_control controllers.
