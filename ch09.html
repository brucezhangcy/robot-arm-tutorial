Chapter 9

Real Hardware Transition

Every chapter to this point could be completed entirely in simulation. This chapter bridges the gap to physical hardware. You will learn what changes when the Gazebo physics engine is replaced by a real Panda arm: network latency, real-time kernel requirements, E-stop procedures, and the subtle but important ways the FCI differs from the simulation interface. The transition checklist in this chapter is a practical reference to return to before every hardware session.

9.1 Simulation vs. Real Hardware

Gazebo faithfully emulates the ROS 2 interface so that the same Python code runs in simulation and on hardware. However, several important differences emerge when you plug in the real arm:

Table 9.1 — Key differences between simulation and real hardware
Aspect Simulation (Gazebo) Real Panda Hardware
Control loop rate 1 kHz (software-limited, may drop under load) 1 kHz (hard real-time, PREEMPT_RT kernel required)
Communication Shared memory (same machine) 1 Gbps Ethernet, dedicated NIC, FCI protocol
Gravity compensation Perfect model; no sag Real dynamics; slight drift possible if model is imperfect
Joint noise None (ideal encoder) Encoder quantisation noise at 12-bit resolution
Collision detection Gazebo physics; ignores franka_ros2 reflexes Hardware reflexes: 10 N contact threshold, joint torque limits
Safety interlocks None E-stop button, deadman pedal, software watchdog
Latency (round-trip) < 0.1 ms 0.3–0.6 ms over dedicated Ethernet

9.2 Network & Communication Setup

The Panda's Franka Control Interface (FCI) requires a direct, dedicated Gigabit Ethernet connection between the robot's base unit and the control PC. The FCI uses a proprietary UDP-based protocol to exchange 1 kHz control packets; sharing that NIC with regular network traffic introduces jitter that triggers the robot's watchdog and causes protective stops.

9.2.1 Network Configuration

# Assign a static IP to the FCI NIC (adapt interface name as needed)
sudo ip addr add 192.168.1.100/24 dev eth0
sudo ip link set eth0 up

# Set maximum transmission unit to 1500 (standard Ethernet)
sudo ip link set eth0 mtu 1500

# Verify link speed is 1000 Mbps (gigabit)
ethtool eth0 | grep -i speed

# Ping the robot (default FCI IP is 192.168.1.1)
ping -c 4 192.168.1.1

9.2.2 Real-Time Kernel Verification

# Confirm the PREEMPT_RT kernel is running
uname -r
# Expected output contains "rt" e.g.: 5.15.0-91-realtime

# Check scheduling policy of the franka_ros2 process
chrt -p $(pgrep -f franka_ros2)
# Should show: scheduling policy: SCHED_FIFO, priority: 80–90

# Monitor latency histogram (run for ~60 s, then Ctrl+C)
sudo cyclictest -l 1000000 -m -n -p 90 -t 1 --histogram=200

9.3 Safety Procedures

Emergency stop. The Panda E-stop cuts motor power within 1 ms. After an E-stop event, the robot enters an error state. Recovery requires: (1) release the E-stop, (2) call ros2 service call /error_recovery franka_msgs/srv/ErrorRecovery, (3) re-activate controllers via ros2 control switch_controllers.

9.3.1 Adjusting Collision Thresholds

The Panda's built-in reflexes trigger a protective stop when joint torques or Cartesian contact forces exceed thresholds. Defaults are conservative (10 N contact force). You can loosen them for tasks that require deliberate contact: 

from franka_msgs.srv import SetForceTorqueCollisionBehavior
import rclpy

def set_collision_thresholds(node, force_n: float = 20.0,
                              torque_nm: float = 20.0) -> None:
    """Raise contact force and torque thresholds (use carefully)."""
    client = node.create_client(
        SetForceTorqueCollisionBehavior,
        '/set_force_torque_collision_behavior')
    client.wait_for_service(timeout_sec=5.0)

    req = SetForceTorqueCollisionBehavior.Request()
    # Lower thresholds trigger a reflex stop; upper thresholds a hard stop
    req.lower_force_thresholds_nominal = [force_n] * 6
    req.upper_force_thresholds_nominal = [force_n * 2] * 6
    req.lower_torque_thresholds_nominal = [torque_nm] * 7
    req.upper_torque_thresholds_nominal = [torque_nm * 2] * 7
    client.call_async(req)

9.4 Hardware Bringup

9.4.1 Launch Sequence

# Terminal 1: launch franka_ros2 with hardware (not simulation)
ros2 launch franka_bringup franka.launch.py \
    robot_ip:=192.168.1.1 \
    use_fake_hardware:=false

# Terminal 2: start MoveIt 2 for the real robot
ros2 launch franka_moveit_config moveit.launch.py \
    robot_ip:=192.168.1.1 \
    use_fake_hardware:=false

# Terminal 3: start RViz for monitoring
ros2 launch franka_moveit_config moveit_rviz.launch.py

# Terminal 4: load and activate controllers
ros2 run controller_manager spawner joint_trajectory_controller
ros2 run controller_manager spawner joint_state_broadcaster

9.4.2 Homing the Robot

# Send arm to the ready pose (joints at zero-torque configuration)
ros2 topic pub --once /arm_controller/joint_trajectory \
    trajectory_msgs/msg/JointTrajectory \
    "{joint_names: [panda_joint1, panda_joint2, panda_joint3,
                    panda_joint4, panda_joint5, panda_joint6, panda_joint7],

9.4.3 Verifying the Connection in Python

import rclpy
from rclpy.node import Node
from sensor_msgs.msg import JointState

class HardwareCheck(Node):
    def __init__(self):
        super().__init__('hardware_check')
        self._received = False
        self.create_subscription(
            JointState, '/joint_states', self._cb, 10)

    def _cb(self, msg: JointState) -> None:
        if not self._received:
            self.get_logger().info(
                f'Joint state received: {[f"{p:.3f}" for p in msg.position]}')
            self._received = True

def main():
    rclpy.init()
    node = HardwareCheck()
    rclpy.spin_once(node, timeout_sec=3.0)
    if not node._received:
        node.get_logger().error(
            'No /joint_states received. Check FCI connection.')
    node.destroy_node()
    rclpy.shutdown()

if __name__ == '__main__':
    main()

9.5 Latency & Timing

Latency matters at 1 kHz: a 1 ms delay is an entire control cycle. Figure 9.3 compares typical round-trip latencies for the operations you have used throughout this tutorial, across simulation and real hardware.

The practical implication: any code that works in simulation at 200 Hz will work on the real hardware — the FCI latency is small enough to ignore. The critical constraint is the PREEMPT_RT kernel, which ensures your 1 kHz loop is not delayed by OS scheduling jitter.

9.5.1 Measuring Your Loop Period

import time
import rclpy
from rclpy.node import Node

class LoopTimer(Node):
    """Measure actual control loop period vs. target."""
    def __init__(self, target_hz: int = 200):
        super().__init__('loop_timer')
        self._target_dt = 1.0 / target_hz
        self._prev      = time.perf_counter()
        self._periods   = []
        self.create_timer(self._target_dt, self._tick)

    def _tick(self) -> None:
        now    = time.perf_counter()
        period = (now - self._prev) * 1000.0  # ms
        self._periods.append(period)
        self._prev = now
        if len(self._periods) >= 1000:
            avg = sum(self._periods) / len(self._periods)
            mx  = max(self._periods)
            self.get_logger().info(
                f'Loop period: avg={avg:.2f} ms  max={mx:.2f} ms '
                f'(target={self._target_dt*1000:.2f} ms)')
            self._periods.clear()

def main():
    rclpy.init()
    rclpy.spin(LoopTimer(target_hz=200))
    rclpy.shutdown()

if __name__ == '__main__':
    main()

9.6 Code Examples

9.6.1 Simulation-to-Hardware Switch Pattern

Use a single use_sim flag to toggle between simulation and hardware. This pattern avoids duplicating code and makes it easy to switch environments: 

#!/usr/bin/env python3
"""
hw_switch.py — identical code runs in sim or on hardware.

Launch with: python hw_switch.py --use-sim   (Gazebo)
         or: python hw_switch.py             (real Panda)
"""
import argparse
import rclpy
from rclpy.node import Node
from geometry_msgs.msg import PoseStamped
import moveit_py
from moveit.planning import MoveItPy

ROBOT_IP = '192.168.1.1'


def build_target(x: float, y: float, z: float) -> PoseStamped:
    p = PoseStamped()
    p.header.frame_id  = 'panda_link0'
    p.pose.position.x  = x
    p.pose.position.y  = y
    p.pose.position.z  = z
    p.pose.orientation.x = 1.0   # pointing down
    p.pose.orientation.w = 0.0
    return p


class ArmNode(Node):
    def __init__(self, use_sim: bool):
        node_name = 'arm_sim' if use_sim else 'arm_hw'
        super().__init__(node_name)

        # MoveItPy initialisation is identical for sim and hardware.
        # The difference is in the launch files used to start franka_ros2.
        self.moveit: MoveItPy = moveit_py.MoveItPy(node_name=node_name)
        self.arm = self.moveit.get_planning_component('panda_arm')
        self.get_logger().info(
            f'Running on {"simulation" if use_sim else "real hardware"}.')

    def move(self, x: float, y: float, z: float,
             vel_scale: float = 0.2) -> bool:
        self.arm.set_start_state_to_current_state()
        self.arm.set_goal_state(
            pose_stamped_msg=build_target(x, y, z),
            pose_link='panda_hand')

        from moveit.planning import PlanRequestParameters
        params = PlanRequestParameters(self.moveit, 'panda_arm')
        params.max_velocity_scaling_factor     = vel_scale
        params.max_acceleration_scaling_factor = vel_scale * 0.5

        plan = self.arm.plan(single_plan_parameters=params)
        if not plan:
            self.get_logger().error('Planning failed.')
            return False
        result = self.moveit.execute(plan.trajectory, controllers=[])
        return bool(result)


def main():
    parser = argparse.ArgumentParser()
    parser.add_argument('--use-sim', action='store_true',
                        help='Use Gazebo simulation instead of real hardware')
    args, _ = parser.parse_known_args()

    rclpy.init()
    node = ArmNode(use_sim=args.use_sim)
    rclpy.spin_once(node, timeout_sec=1.0)

    # Move to a sample target — same code, sim or hardware
    success = node.move(x=0.4, y=0.0, z=0.5, vel_scale=0.15)
    node.get_logger().info(f'Motion {"succeeded" if success else "failed"}.')

    node.destroy_node()
    rclpy.shutdown()


if __name__ == '__main__':
    main()

Exercises

  1. Run cyclictest on your control PC with and without the PREEMPT_RT kernel. Compare the 99th-percentile latency. What is the worst-case jitter without the RT kernel, and would it affect the 1 kHz control loop?
  2. Using loop_timer.py, measure the actual period of a 1 kHz timer on your machine. What is the maximum observed period? How much margin does this leave before the watchdog (500 ms timeout) triggers?
  3. Trigger an E-stop intentionally (e.g., push the red button) while a joint trajectory is executing. Observe the arm behavior and the ROS log output. Then write the recovery procedure from memory without referring to the text.
  4. Modify hw_switch.py to add a --vel-scale argument and test with values from 0.05 to 0.5. On real hardware, compare the motion at low speed to simulation: does it feel smoother or rougher? Why?

Key Terms

PREEMPT_RT
A Linux kernel patch that makes the kernel fully preemptible, reducing scheduling jitter to enable hard real-time operation at 1 kHz.
Franka Control Interface (FCI)
The UDP-based protocol over Gigabit Ethernet that allows external computers to stream 1 kHz control commands to the Panda base unit.
Protective stop
A reversible stop triggered by a reflex (contact force, velocity limit, or watchdog timeout); recoverable via error-recovery service call.
Emergency stop (E-stop)
A hard stop that cuts motor power within 1 ms; requires manual release and software recovery before motion can resume.
Watchdog timer
The FCI safety mechanism that triggers a protective stop if no control packet arrives within a fixed timeout (default 1 ms).
EtherCAT
The real-time industrial Ethernet bus used internally between the Panda base unit and the seven joint motor drives.
cyclictest
A standard Linux real-time benchmark tool that measures scheduling latency by waking a high-priority thread at precise intervals.
Collision threshold
A configurable force or torque limit; when exceeded by a measured value, the controller triggers a protective stop reflex.
